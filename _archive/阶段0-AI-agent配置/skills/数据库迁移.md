# 技能：数据库迁移

> 适用：工程负责人
> 目标：让 schema 变更可审、可回滚、不影响生产。

## 1. 触发场景

- 新增 / 修改表 / 字段
- 加索引
- 改 enum
- 改默认值

## 2. 前置

- 阅读 [`docs/03-rules/数据库规范.md`](../docs/03-rules/数据库规范.md)
- 在 staging 验证

## 3. 流程

### 3.1 改 Schema

在 `prisma/schema.prisma` 改：

- 加列（默认 NULL，加完再补默认）
- 加索引（unique / 组合）
- 加表
- 改关系

### 3.2 生成迁移

```bash
pnpm prisma migrate dev --name <描述>
```

- 名字用英文，kebab-case，描述清楚
- 例：`add-ai-conversations`、`add-index-orders-user-id`

### 3.3 检查 SQL

- 看 `prisma/migrations/<timestamp>_<name>/migration.sql`
- 评估：
  - 是否会锁表（`ALTER TABLE ADD COLUMN` 不会，但 `ALTER TYPE` 会）
  - 是否会在大表上建索引（用 `CONCURRENTLY`）
- 如需手改 SQL，在 PR 描述里说清楚

### 3.4 测试

1. 在 staging 跑：
   ```bash
   pnpm prisma migrate deploy
   ```
2. 跑 smoke test
3. 跑全量 e2e

### 3.5 备份生产（重大变更）

- 重大变更前在生产做 `pg_dump` 到 OSS
- 命名：`backup-pre-<migrate-name>-<timestamp>.sql.gz`

### 3.6 部署

CI 步骤（`db-migrate.yml`）：

1. 选环境（preview / staging / production）
2. 跑 `prisma migrate deploy`
3. 跑 `prisma generate`
4. 跑 `pnpm build`（确保类型对得上）
5. 部署应用

### 3.7 验证

- 应用启动正常
- 新字段在 API 响应中出现
- 无 Sentry 错误
- 关键查询性能

### 3.8 记录

- 在 PR 描述里写：
  - 改了什么
  - 影响范围
  - 回滚步骤
- ADR（如涉及 schema 重大重构）

## 4. 破坏性变更

不允许的：

- 删列 / 改类型（在生产）
- 删 enum 值
- 改主键

如果必须：

1. 加新列 → 同步双写 → 切读 → 删旧列（多版本）
2. 用 `prisma migrate resolve --rolled-back` 处理
3. ADR 详写

## 5. 验收

- [ ] 迁移文件清晰
- [ ] staging 验证通过
- [ ] 备份已做（重大变更）
- [ ] CI 全绿
- [ ] 生产部署后 smoke test 通过
- [ ] 监控无异常

## 6. 反模式

- ❌ 跳过 staging 直接生产
- ❌ 一张大表加非空列（会锁表）
- ❌ 删数据列（用软删）
- ❌ 改列类型而不写双写
- ❌ 不写 ADR

## 7. 速查

| 任务 | 命令 |
|---|---|
| 生成迁移 | `pnpm prisma migrate dev --name <name>` |
| 部署迁移 | `pnpm prisma migrate deploy` |
| 重置本地 | `pnpm prisma migrate reset` |
| 备份 | `pg_dump ... > backup.sql.gz` |
| 恢复 | `pg_restore ... backup.sql.gz` |
