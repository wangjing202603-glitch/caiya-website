# 技能：事故复盘

> 适用：事件指挥官 + 团队
> 目标：让每次事故被认真复盘，转化为可执行改进。

## 1. 触发

- P0 / P1 事故
- 重复出现 ≥ 2 次的问题
- 客户 / 监管投诉

## 2. 流程

### 2.1 启动

- 事件关闭后 1 周内
- 召集所有相关方
- 选记录员

### 2.2 复盘会（1 小时）

议程：

1. 重建时间线（5 分钟）
2. 现象 + 影响（5 分钟）
3. 根因分析（20 分钟）
4. 改进措施（20 分钟）
5. 分配责任 + 截止日期（10 分钟）

### 2.3 写文档

文件命名：`memory/事故复盘/YYYY-MM-DD-<简短标题>.md`

使用以下模板（**不要省略任何一节**）。

## 3. 复盘模板

```markdown
# 事故复盘：<标题>

> 日期：YYYY-MM-DD
> 级别：P0 / P1 / P2
> 事件指挥官：@xxx
> 记录员：@xxx
> 相关 PR / 告警 ID：#xxx

## TL;DR（一段话）

用 1~2 句话讲清楚：发生了什么、影响多大、什么时候恢复。

## 时间线

- `2026-07-15 10:00` 用户首次报告
- `2026-07-15 10:05` 监控告警触发
- `2026-07-15 10:10` IC 介入，开 incident 频道
- `2026-07-15 10:30` 定位根因
- `2026-07-15 10:45` 止血完成（Vercel 回滚）
- `2026-07-15 11:00` 服务恢复
- `2026-07-15 12:00` 通知用户
- `2026-07-15 18:00` RCA 草稿

## 影响

- 用户数：约 X 人
- 持续时间：X 分钟
- 收入影响：约 ¥X（如可量化）
- 数据丢失 / 损坏：是否有
- 客诉 / 监管事件：是否有
- 公关：是否需要发声明

## 根因（5 Whys）

> 1. 为什么 1 发生了？→ 因为 ...
> 2. 为什么 2？→ 因为 ...
> 3. 为什么 3？→ 因为 ...
> 4. 为什么 4？→ 因为 ...
> 5. 为什么 5？→ 根本原因：...

## 修复

- 短期（已做）：...
- 中期（1 周内）：...
- 长期（1 个月内）：...

## 改进项（可执行）

| # | 行动 | 负责人 | 截止 | 状态 |
|---|---|---|---|---|
| 1 | ... | @xxx | YYYY-MM-DD | 待启动 |
| 2 | ... | @xxx | YYYY-MM-DD | 待启动 |

## 经验

- 我们学到了什么？
- 之前是否有过类似信号被忽略？
- 监控 / 流程 / 工具的改进点？

## 预防

- 自动化测试 / 监控 / 文档更新
- 是否需要新的告警
- 是否需要重写某个流程

## 链接

- Sentry issue：...
- Vercel deployment：...
- GitHub PR：...
- Slack / 飞书频道：#inc-...
```

## 4. 复盘后动作

- 改进项在 GitHub 建 Issue → 加到对应 milestone
- 文档同步到 [`memory/历史经验.md`](../memory/历史经验.md)
- ADR（如涉及架构）
- 季度 review 全部改进项进度

## 5. 验收

- [ ] 复盘文档完成
- [ ] 改进项已建 Issue
- [ ] 负责人 + 截止日期清晰
- [ ] 关键监控已加
- [ ] 关键测试已加
- [ ] 团队 review 通过

## 6. 反模式

- ❌ "是用户的网络问题"——很少是
- ❌ 找"替罪羊"——找系统问题
- ❌ 不写"预防"——下次还会
- ❌ 改进项无 owner——会失访
